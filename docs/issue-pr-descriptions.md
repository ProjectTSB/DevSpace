# Issue・PR本文の書き方

DevSpace・Asset・TheSkyBlessingのIssue・PRを作成・更新するときの共通規約。

## 読者と目的

本文は、その会話や作業依頼を知らない開発者が読むものとして書く。Issueは問題の把握・再現・対応方針の検討に、PRは変更の理解・レビュー・マージ判断に必要な情報を伝える。後から経緯を調べる開発者も読者に含める。

冒頭で具体的な問題や目的を述べ、その判断に必要な情報を続ける。「整理した」「改善した」だけで終えず、何がどう扱えるようになるのかを書く。

## 共通の方針

- **対象そのものを説明する。** 依頼者への返答、会話の引用、作業の進捗報告を本文へ持ち込まない。「指示どおり」「今回頼まれた範囲」「先ほどの変更」といった表現を使わず、機能・条件・挙動を具体的に書く。
- **判断に必要な情報を選ぶ。** 書く前に「この情報で、読者のどの判断が変わるか」を確かめる。差分から分かるファイル一覧や、読んだ資料の件数を説明の代わりにしない。
- **事実と推測を分ける。** 実測した挙動、コードから読み取った挙動、推定した原因を区別する。調査依頼もIssueにできるが、未確認の原因を確定した不具合として書かない。
- **根拠を読者が辿れるようにする。** 関係するIssue・PR、コード、再現手順、必要なログへ直接リンクする。特定時点のコードを根拠とする場合はcommit固定のリンクを使う。ローカルの絶対パスや共有されていない実行記録を唯一の根拠にしない。
- **長さと構成は内容に合わせる。** 小さな変更は短い段落でよい。比較、再現手順、独立した変更点など、読みやすくなる場合に見出し・箇条書き・表を使う。空の節や「該当なし」を並べない。投稿先にテンプレートがあれば、その構成も確認する。

## Issueに書くこと

### 不具合

冒頭に「どの条件で何が起き、何が困るか」を書く。本文には次の情報を、再現・対応に必要な範囲で含める。

| 情報 | 書く内容 |
| --- | --- |
| 期待と実際 | 期待する挙動と、観測またはコード上で確認した挙動の違い。期待の根拠となる仕様があれば添える |
| 発生条件・再現方法 | 対象の版、必要な設定・状態、操作、結果の確認方法。再現に影響する環境情報を選ぶ |
| 影響 | プレイヤーや後続処理への具体的な影響。頻度・規模を推測で誇張しない |
| 原因・対応案 | 判明している原因とその根拠。提案する修正方法があれば、実際の症状とは分けて書く |

実行再現がなくても、コード上の条件と結果を具体的に示せる場合は、その根拠で報告する。ゲーム内で確認したかのような再現結果は作らない。原因が不明でも、観測と再現条件を共有できればIssueとして成立する。

### 機能提案・改善・調査

「現状のどこで困るか」「実現したい状態」「完了を判断できる条件」を書く。実装方式に選択の余地がある場合、要求する挙動と実装案を分ける。

調査Issueは、答えたい問いと、その答えによって決めたいことを明確にする。すでに分かっている条件や根拠を添え、漠然とした「要調査」だけを残さない。

独立に判断・完了できる問題は別Issueにする。共通原因や一体の仕様として扱う必要がある場合は、その関係を説明する。

## PRに書くこと

冒頭に「解決する問題・目的」と「変更後の挙動」を書く。具体的な発生条件と変更前後の例で説明できる場合は、その例を使う。

続けて、差分だけでは分かりにくい設計理由や、レビューで押さえるべき変更点を書く。関数ごとの変更履歴を列挙するのではなく、変更が目的をどう満たすかを説明する。

- 関連Issueがあればリンクする。解決する範囲と一致する場合だけ、Issueを閉じる指定を使う。
- 互換性、利用手順、移行、他PRへの依存など、利用やマージ順序に影響する条件があれば示す。
- 検証は、変更のどの性質を、どの方法で確認し、どうなったかを書く。小さな変更では一文で足りる。再実行に必要ならコマンドやシナリオを添える。
- 静的確認・自動テスト・実サーバーでの確認は、方法が分かるように記述する。「検証済み」の一語で範囲を広げない。例えば起動スクリプトの委譲をstubで確認した場合は、その確認内容を書く。
- 検証で判明した問題や、判断を左右する未確定事項は、影響と必要な対応を具体的に書く。一般的な未実施項目の一覧は作らない。
- 差分の目的や構成が変わったら、タイトルと本文も最終的な変更に合わせて書き直す。

文書のPRでは、読者が得られる情報と使う場面を説明する。誤記の訂正なら、誤っていた説明と正しい契約を示す。文書を追加した件数だけで価値を説明しない。

## 本文へ持ち込まない作業情報

依頼者へ返す完了報告と、Issue・PRの本文は別々に書く。次の情報は通常、本文には不要である。

- 別作業として残した実装、混在していた差分、退避や切り分けの経緯。
- 「機能変更は含めていない」「サーバーを再起動していない」など、変更の理解や判断に結び付かない不実施の列挙。
- Agentやモデルの分担、ツール操作の順序、調査にかけた時間、読取・リンク確認の件数。
- 試行錯誤の時系列、採用しなかった案の一覧、依頼者へ向けた約束の履行報告。

採用理由を理解するのに必要な選択肢との比較や、他の変更を先に取り込む必要性は、設計理由・依存関係として説明する。作業中に起きたことをそのまま載せる理由にはしない。

## 書き換え例

以下は表現の例であり、検証結果は実際に確認した内容へ置き換える。

| 作業報告に寄った表現 | 読者の判断に役立つ表現 |
| --- | --- |
| 指示どおりナレッジだけをまとめ、神器の実装は除外しました | Mob／Objectの継承とFieldの寿命を、実装・レビュー時に参照できるよう文書化します |
| 299件のリンクを確認し、ゲーム内検証はしていません | 文書の参照先と見出しの対応を確認しました |
| いろいろ調べた結果、毎回呼ばれるバグだと思います | MPが500のとき、表示レベル50と生のMPを比較するため、表示が一致していても更新処理へ進みます |

## 投稿・更新前の確認

1. 会話を読んでいない人が、問題・目的と対象を理解できるか。
2. Issueなら再現・対応、PRならレビュー・マージの判断に必要な情報があるか。
3. 主張の強さが根拠に合っており、期待・実測・推測を混同していないか。
4. 作業報告、不必要な不実施の列挙、古い方針の説明が残っていないか。
5. タイトル・本文・現在の差分または調査結果が一致し、参照先を読者が開けるか。
