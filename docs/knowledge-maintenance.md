# ナレッジの配置と更新

## 読み始める場所

| 開いたリポジトリ | 毎回の規約 | 領域別の案内 |
| --- | --- | --- |
| DevSpace | [AGENTS.md](../AGENTS.md) | [README.md](../README.md) |
| TheSkyBlessing | [AGENTS.md](../TheSkyBlessing/AGENTS.md) | [開発ナレッジ](../TheSkyBlessing/docs/knowledge/README.md) |
| Asset | [AGENTS.md](../Asset/AGENTS.md) | [開発ナレッジ](../Asset/docs/knowledge/README.md) |

各 repo に `AGENTS.md` を置き、実装・レビュー・調査の依頼内容から必要な詳細文書を Agent が選び、判断前に読むよう指示する。ユーザーは普段の作業依頼だけを伝え、文書名や読む指示を毎回追加する必要はない。Codex は起動時に通常 Git ルートから作業ディレクトリまでの指示を集めるため、DevSpace だけに入口を置かず、各独立 repo にも入口を持たせる。指示を追加・変更した後の確認は新しいセッションで行う。[公式の指示探索仕様](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

自動で指示に含まれる AGENTS.md と、そこから参照する詳細文書は区別する。`docs/knowledge/*.md` の本文を自動展開する設定にはしておらず、Agent が AGENTS.md の必読案内に従ってファイルを読む方式である。DevSpace から開始した場合も、子 repo の全文が起動時に一括投入される前提にせず、親の案内から子 repo の入口を読む。

`CLAUDE.md` は `@AGENTS.md` で本文を共有する。今回の対象は TheSkyBlessing と Asset。Asset-AnimatedJava 自体の体系的な知識整理は対象外だが、Asset からの呼出規約は Asset 側で扱う。

Mob／Object／Effect の変更では、Asset 側の [型・インスタンス・継承モデル](../Asset/docs/knowledge/object-model.md) を起点にする。本体側の [Asset の実行モデル](../TheSkyBlessing/docs/knowledge/asset-runtime.md) は dispatch、Field の保存、context の退避・復元を扱う。個別関数の手順に加え、親の契約と個体の状態を確認する。

本体の機能追加や領域をまたぐ変更では、[本体の抽象構造](../TheSkyBlessing/docs/knowledge/architecture.md) から、定義・個体状態・snapshot・寄与と導出値・イベント・呼出 context の境界を確認する。既存のどの拡張点へ変更を載せるか、誰が状態を保存・解除するかを判断するための入口である。配置・解呪・転移・商人・コンテナは [World コンポーネント](../TheSkyBlessing/docs/knowledge/world-components.md)、アイテム・回収・Mob 転送・計算部品は [Runtime コンポーネント](../TheSkyBlessing/docs/knowledge/runtime-components.md) から、その領域固有の所有・更新・受け渡しを確認する。

## 更新時に残すもの

目的は次回のコード実装・レビューで、同じ誤実装や見落としを防ぐことである。実装、レビューだけの作業、不具合調査、ユーザーによる訂正を記録の契機とし、再利用できる発見はその作業内で保存する。ユーザーによる個別の記録依頼を必要としない。

新しい知見を規約へ取り込むときは、次の情報を対象 repo の文書に残す。

1. **適用範囲**：対象パスや作業内容。個別の神器・Mob の事情を全体の禁止事項にしない。
2. **理由と失敗例**：何が壊れるのか、どの実行主体や一時データに依存するのか。
3. **現行の実例**：repo 内のファイルへの相対リンク。API は引数・戻り値・呼出前提・後始末を確認する。
4. **出典と結論**：PR / レビューコメントの直接 URL、採用状況、現行コードとの対応。未マージ案・解決していない議論は規約と区別する。
5. **検証方法**：生成差分確認・ゲーム内確認・GitHub Actions の結果確認のうち、どこまで実施すればよいか。

常に必要なら `AGENTS.md` 本文、領域限定なら `docs/knowledge/` と必読対応表を更新する。source 一覧だけに根拠を集めず、規約の近くから辿れるようにする。詳細文書をすべて毎回読む構成にはしない。

レビューは過去の文脈を含むため、コメントをそのまま現在の仕様としてコピーしない。実装変更で規約が古くなった場合は、該当本文と出典の現行対応を一緒に更新する。

ProjectTSB Wiki の設計意図・作成規約も根拠に含める。[本体の照合記録](../TheSkyBlessing/docs/knowledge/wiki-crosscheck.md) と [Asset の照合記録](../Asset/docs/knowledge/wiki-crosscheck.md) にページ別の採否を記録している。Wiki に明記された規約、現行実装との差、コードから追加した補足を区別し、実装が規約を強制しないことだけを理由に規約を取り消さない。

## 作業完了前の確認

1. 作業で判明した前提、ユーザーからの訂正、レビューの見落とし、検証で発見した原因を振り返り、次の開発に使う知見を選ぶ。新しい知見がなければ更新は不要。
2. 対象領域の既存文書へ統合し、誤った本文と関連箇所を訂正する。適用範囲と根拠を付け、作業履歴だけを増やさない。未確定の提案は確定規約と区別する。
3. 更新した説明に入口から到達できること、コード・根拠リンク・他文書との対応を確認する。
4. 完了報告には更新先、または更新不要の理由を短く示す。明示的に編集禁止の作業なら、更新候補と保存先を報告する。

この運用は AGENTS.md の指示に従って作業中の Agent が記録する方式であり、記録漏れを機械的に検出・強制する仕組みではない。作業外に新しく付いた GitHub コメント等を自動収集する処理も、この運用には含めない。完了報告に更新先を含めることで、実際に記録されたか確認できるようにする。

## 共有と検証

TheSkyBlessing / Asset は独立 Git リポジトリなので、各 repo の指示・ナレッジはその repo の変更として共有する。DevSpace のコミットだけでは含まれない。本体・Asset の入口とナレッジは各 repo のローカルコミットへ保存済みである。push は別操作であり、他環境へ配布済みという意味ではない。

新しい worktree は、元の作業ツリーにある未コミットの AGENTS.md やナレッジを自動では引き継がない。並列作業へ渡す前に、対象 worktree の入口・本文・必要な起動設定が揃っているか確認する。共有する状態は各 repo の履歴へ含めるのが基本で、未コミット状態を使う必要がある場合は、対象と基準を明示して必要な差分・未追跡ファイルを作業コピーへ渡す。既存の変更を上書きしたり、元 repo へのリンクで編集内容まで共有したりしない。以前の worktree 読込検証も、未コミット文書を検証先へ明示的にコピーした条件である。

並列の実装では担当する repo・ファイル・共通 ID／alias／tag の変更責任と、統合する担当を分ける。各担当が得た知見はその作業コピーへ残し、統合時に sources.md や AGENTS.md を含む文書の重複・矛盾も整理する。これらは作業時の調整であり、worktree 作成だけで自動実行される処理ではない。共通サーバーの設定・検証順序は [README の起動手順](../README.md#起動) に従う。

文書更新時は、相対リンク、例のパス、出典との対応、入口からの必読経路を確認する。読み込みの確認では、対象 repo を作業ディレクトリとした新しい Agent セッションに、最初から見えている規約と変更対象に対する必読文書を答えさせる。文書の存在と、実際のセッションに指示が渡ったことを区別する。実施結果は [知識の検証記録](knowledge-verification.md) に記載する。

検証では、開始時に渡る指示の確認、誘導なしの文書参照、読ませた後の適用を区別する。自発的な参照を測る場合は、検証プロンプトに文書名、読む指示、必読文書を答える指示を加えず、通常の作業依頼から実際の読取ログを確認する。読むよう指定した検証の結果を、通常依頼での自発的な参照の根拠にしない。
