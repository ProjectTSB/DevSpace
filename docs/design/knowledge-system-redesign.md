# ナレッジ運用の再設計

状態: 採用した設計方針の記録。実装後の現行の運用規則は [AGENTS.md](../../AGENTS.md)、[ナレッジの配置と更新](../knowledge-maintenance.md)、[ナレッジのノートとINDEX](../knowledge-notes.md) を正本とし、この文書を規約の代わりに読まない。

## 目的と対象

AIが通常の実装・レビュー・調査・ユーザーからの訂正で、利用者に文書名や記録を指示されなくても必要な知識を参照し、再利用できる判断を更新できるようにする。同じ大きな文書へ変更が集中する状態を減らし、根拠のない追記、検索漏れ、古い契約の再利用も抑える。

対象はDevSpaceの共通規約と、Asset・TheSkyBlessingのコード固有ナレッジとする。TSB-ResourcePackやAsset-AnimatedJavaの体系的な整理は含めない。既存の正本の分担を維持する。共通規約・AI運用はDevSpace、コード固有の契約と設計理由は対象repoの作業コピー、本体APIの契約は提供側のTheSkyBlessingに置く。利用側には固有の使い方と提供側への参照を残す。

## 参照経路とノート

DevSpaceの`AGENTS.md`と`CLAUDE.md`を常時参照の入口にし、AIが依頼から対象repo・作業コピー・領域を選ぶ。対象repoの`docs/knowledge/README.md`は、領域と横断参照を案内する。重要なAPI契約や構造の概要は、検索結果だけに依存させず、必要な領域文書から辿れる状態を保つ。詳細なノートは、その作業コピーのコードと同じブランチに置く。

ノートにはタイトルと、どの作業で読むかを一文で示す`description`を必須とする。対象パス・識別子など、発見に役立つ短い情報は必要なノートだけに付ける。根拠、適用条件、適用外の条件、関連する契約への参照は本文に残す。`verified_at`や主観的な`confidence`を全ノートの必須項目にしない。原則は一つの判断を一つのノートで扱う。ただし、前提・結果・後始末を一緒に理解する必要がある契約は分断しない。

ノートを探すたびに、対象作業コピーのノートからタイトル・`description`などのヘッダーだけを機械的に抽出してINDEXを生成する。INDEXのファイルや手書きのノート一覧は保存しない。生成結果にはノートへのパスを含め、対象領域を絞って読めるようにする。該当が見つからないときは探索範囲を広げ、コードと提供側の契約を確認してから知識の有無を判断する。選んだノートの関連契約も本文まで読む。ブランチ変更後は、その作業コピーからINDEXを再生成する。

機械的に判定できる規約には差分の検査を、実行して確かめる振る舞いには既存の検証シナリオを使う。ただし、検査やシナリオだけでは選択理由・適用条件を伝えられない場合、その説明は残す。機能固有の値や演出は機能側へ置き、コードを言い換えただけの説明は整理する。既存文書は一括して細分化せず、内容・根拠・参照経路を保てる単位で移す。

## 自律更新と品質

採用判断には現行の三条件「次のどの作業で何の判断を変えるか」「根拠と適用条件は何か」「既存の説明と何が違うか」を使う。実際の失敗や利用者の決定は強い根拠だが、それだけを採用条件にはしない。根拠が足りない候補や未採用案は、現行契約のノートへ入れない。既存の説明が誤っていれば元の記述を直し、同じ内容のノートを増やさない。

AIは作業の終了前に知見を選別し、承認待ちを挟まず対象作業コピーの正本へ反映する。新しい規約・契約については、根拠の対象版、提供側との一致、既存説明との矛盾、適用外の条件を別のAIによる確認と機械的な検査で点検する。検索用ヘッダーの形式、参照先、ノート本文との対応も検査する。人による全ノートの逐次承認は求めない。

レビュー指摘、不具合、検証失敗が後から分かったときは、AIが「知識の欠落」「存在したが見つからなかった」「読んだが誤用した」「記述自体が誤っていた」を区別する。原因に応じてノート、ヘッダー、参照経路、検査、シナリオを直す。指摘をそのまま新しいノートに転記しない。作業外のGitHubイベントを常時監視する仕組みは今回の必須範囲とせず、通常のレビュー対応・不具合調査で追加の記録指示なしに反映する。

## 人がマージする変更

以後のAI全体の行動を変える文書・設定は、AIが通常のPRを完成させ、人がマージする。別途Approve操作は要求しない。対象にはDevSpaceの`AGENTS.md`、知識の採用・配置規則、参照経路とINDEX生成の規則、子repoの入口の必読条件、自動マージ条件を含める。保護対象を普通のノートへ移して人のマージを回避しない。個別ノートの追加・訂正・削除と、その検索用ヘッダーの更新は承認待ちにしない。

Asset・TheSkyBlessingでは、現在`docs/`と`tests/`のPRを自動マージする。保護対象を含むPRは自動マージから外す。Assetの既存ブランチ規則で必要なBot承認は維持してよいが、マージは人が行う。DevSpaceでは現在、共通知識を`main`へ直接反映する。保護対象だけは作業ブランチからPRに切り替え、人によるマージを待つ。通常の共通知識の直列統合と子repoのブランチ管理は維持する。AIは保護対象のPRを自分でマージしたり、自動マージを設定したりしない。

## 実装と完了の条件

Claude CodeはDevSpaceを開始位置とし、対象repoごとに現在のブランチ・差分・リモートとの差を確認する。既存の作業ブランチや未追跡ファイルを保持し、必要なら独立した作業コピーを作る。子repoの`master`へ直接コミットしない。開発用スクリプトの保存先と再実行条件は[開発用スクリプトの作成と保存](../script-development.md)に従う。

INDEX生成は対象ブランチのヘッダーだけを入力とし、再実行しても追跡ファイルやGit indexを変更しない。通常の依頼から入口、生成INDEX、必要なノート、依存契約へ進めるよう案内を更新する。ノートの品質検査と、保護対象を自動マージしない判定を実装する。既存の文書・リンク・出典・正本を照合し、無理な一括移行や情報の削除をしない。

方式の優劣を測る比較実験は行わない。INDEXの生成と参照、ノートの自律更新、保護対象の自動マージ除外など、実装した経路の基本動作は確認する。既存の必要なテストも実行する。完了時にはrepoごとの差分、確認結果、残る制約、保護対象PRの人によるマージ待ち状態を報告する。実装後はこの文書を現行規約の代わりに使わず、採用された運用を各正本へ反映する。
